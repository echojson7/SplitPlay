# Research 8 (round 2, "max-out"): network transport, protocol, input path
Code read: Sunshine d7e5fe0, moonlight-common-c 5d3c0ec, moonlight-qt ac29686, Apollo adc5c5a (SendInput path), enet (cgutman fork aca8784), nanors. 5 web lookups. Estimates/unverified marked.

## Bottom line
Stock Sunshine send path is already modern: USO (WSASendMsg + UDP_SEND_MSG_SIZE, ≤64 KB / 46 packets per call; misc.cpp:1510-1582, stream.cpp:1679-1683); DSCP via qWAVE (misc.cpp:1663-1771); high-res waitable timer + 0.5 ms timer resolution (misc.cpp:1205, :1814); HIGH_PRIORITY_CLASS; no LAN video encryption by default (config.cpp:844); speculative RFI on loss (client RtpVideoQueue.c:210-222). Real gains: scheduling robustness under N busy games; Sunshine logic gaps (rumble delay, fixed 800 Mbps pacing, 5-frame RFI window, ignored loss telemetry); shared-NIC coordination; client settings delivered as ready-made launch commands.

Budget today on wired LAN (est): input ≈0.5–1 ms client batching (fixed 1 ms, InputStream.c:44) + 0.2–0.5 network + 0.05–0.2 host queue/SendInput. Video serialization = frame bytes / min(800 Mbps, link): 1080p500 @100 Mbps ≈25 KB ≈0.25 ms; 1080p60 @150 Mbps ≈312 KB ≈3.1 ms; IDR ≈1.5–4 ms. Input ≤30 ms / video ≤50 ms targets are bounded by game, compositor, display, client — not transport.

## Ranked ideas (unmodified Moonlight unless "fork")
1. **Worker scheduling hardening** — SetProcessInformation(ProcessPowerThrottling) opt-out of EcoQoS (EXECUTION_SPEED) and IGNORE_TIMER_RESOLUTION; MMCSS ("Games"/"Pro Audio", AvSetMmThreadPriority CRITICAL) for videoBroadcast, controlBroadcast, input, capture/encode threads; power plan min state 100%, no core parking. Today only audio uses MMCSS (audio.cpp:701); network threads ABOVE_NORMAL/HIGHEST in HIGH class = base 14–15 (misc.cpp:1135-1160, stream.cpp:1319, :1543) — ties with a game's TIME_CRITICAL thread in NORMAL class (15) → quantum round-robin. Win11 infers QoS heuristically and may ignore timer requests from non-visible processes; workers are windowless in non-console sessions. Sunshine/Apollo/Vibepollo don't call these. Gain: p99 send/input jitter several ms → sub-ms under N busy games (est, unverified); P-core placement on hybrid (unverified). Cost 1–2 days. MMCSS reserves 20% for non-MMCSS by default; N workers untested.
2. **Rumble/feedback delivery delay** — rumble/LED/HDR messages queued until control loop wakes (stream.cpp:1370-1382); loop blocks in enet_host_service(…,150 ms) (stream.cpp:1395, :763-765); without input only the client's 100 ms ping wakes it (ControlStream.c:302) → haptics lag up to ~100 ms. Fix: 1 ms timeout or loopback "doorbell" socket. Gain ~100 ms → <1 ms worst case. Hours.
3. **Configurable, host-coordinated pacing** — hard-coded 80% of 1 Gbps per session (stream.cpp:1673), each worker unaware of shared NIC. Per-desktop pacing rate; service divides host uplink (shared memory / pipe on client connect). Defaults ≈0.8 × client link; lower for Wi-Fi (800 Mbps bursts into a ~400 Mbps AP lose IDRs); 2–8 Gbps for 2.5/10 GbE. Optional: stagger desktops' capture/send phase by 1/N frame period. Gain: 1080p60/150 Mbps on 2.5 GbE ≈3.1 → 1.2 ms; removes 0.5–3 ms cross-desktop queuing on 1 GbE; fewer Wi-Fi burst losses; ≈0 at 500 fps (frames <71 packets not paced). 2–5 days.
4. **RFI window by time, not frames** — NVENC DPB 5 (H.264/HEVC), 8 (AV1) (nvenc_base.cpp:372, :408, :449); RFI spanning ≥5 frames → IDR (:821). At 500 fps = 10 ms; longer loss-detect+RTT → IDR 150–300 KB burst → more loss. Set DPB ≈16 when fps ≥240 (HEVC L5.2 1080p allows 16; derived) → 32 ms; numRefL0 stays 1. ~1 day + decoder test; maxNumReferenceFrames=1 clients unaffected; some decoders may fail (unverified).
5. **Use ignored client loss telemetry** — per-frame FEC status SS_FRAME_FEC_PTYPE 0x5502 (Video.h:57-70; sent from RtpVideoQueue.c:93-108), pings, RFI/IDR requests; Sunshine only logs IDX_LOSS_STATS (stream.cpp:1190-1204), no 0x5502 handler. Use with ENet RTT for adaptive FEC (20% → 5–10% clean, min 2), adaptive bitrate below client request, adaptive pacing, per-desktop metrics. Gain 10–15% bandwidth on clean links, Wi-Fi resilience, real tuning data. 1–2 weeks; control-loop tuning risk.
6. **Dedicated input thread & SendInput details** — today: control thread decrypts → input_queue → global task pool with 1 normal-priority thread (main.cpp:387, input.cpp:2101, :2240-2262) also running key-repeat/DS4 timers. Per-session input thread TIME_CRITICAL/MMCSS; keep relative-move coalescing (input.cpp:1811); add MOUSEEVENTF_MOVE_NOCOALESCE (Apollo doesn't, input.cpp:540); OpenInputDesktop/SetThreadDesktop only when SendInput fails (Apollo input.cpp:477-505) — not before each injection; per-desktop profile: "Enhance pointer precision" off, pointer speed 10/20 for 1:1 relative. Gain 20–200 µs typical, removes ms tails. 1–3 days.
7. **Send data shards before parity** — today whole FEC block encoded+encrypted before first packet (stream.cpp:1716); send data shards while parity computes; wire order unchanged. Gain ≈0.05–0.5 ms per large frame, up to ~1 ms on IDR (est; measure with frame_fec_latency_logger). 2–3 days.
8. **Host NIC/OS settings by installer** — disable EEE/Green Ethernet; ignore 802.3x pause frames (one congested 1G client port on a cheap 2.5G switch can pause the whole host link; switch-specific, unverified); keep USO + checksum offload (software fallback undocumented, unverified; Sunshine falls back to per-packet sends); NetworkThrottlingIndex=0xffffffff (send-path effect unverified); exclude worker ports/processes from third-party WFP/AV inspection; lab-check DSCP: QOS_NON_ADAPTIVE_FLOW → DSCP only (no 802.1p): video 0x28, audio 0x38, ENet control QOSTrafficTypeControl 0x38 (enet win32.c); Wi-Fi WMM depends on AP DSCP→UP mapping.
9. **Client "launch pack"** — host can't change client settings; defaults: V-sync on (streamingpreferences.cpp:132), frame pacing off, packet size 1392. SplitPlay UI generates moonlight-qt command lines or portable Moonlight.conf (portable.dat, main.cpp:435); CLI has --fps, --bitrate, --no-vsync, --no-frame-pacing, --video-decoder, --packet-size, --video-codec (commandlineparser.cpp:348-373). Advice: V-sync off (D3D11 ALLOW_TEARING, d3d11va.cpp:592-602, :790) or VRR; high-refresh client display even for 60 fps; moderate bitrate at 60 fps. Gain ≈8–16 ms avg at 60 Hz from V-sync off — biggest single win (est).
10. **Encryption** — AES-GCM with AES-NI @150 Mbps ≈1% core; per-packet init (crypto.cpp:184-213) ≈10–50 µs/frame; moonlight-qt opts in with AES accel (session.cpp:686-694). Recommend lan_encryption_mode=1; latency no reason to disable.

## Optional (Moonlight fork)
Unreliable/cumulative mouse packets (every move ENet-reliable, InputStream.c:777; retransmit ≈2× RTT, enet protocol.c:1383 — ~2 ms LAN, ≥10 ms Wi-Fi; advertise via x-ss-general.featureFlags); sub-ms mouse batching with high-res timer instead of SleepEx(1) (Platform.c:105), ≈0.3–0.5 ms; >1 kHz mice currently add nothing; delay-gradient feedback for congestion control; slice-level streaming/decoding (protocol needs total frame size & FEC block count in first packet, stream.cpp:1593 multiFecBlocks) ≈1–2 ms @60; client URO/batched receive for weak clients at 1440p500/300 Mbps (~27k pps).
