# SplitPlay — архитектурный документ (Этап 1)

Версия 0.1 · 2026-10-28 · статус: на согласовании

SplitPlay превращает один ПК с Windows в N независимых рабочих столов. Каждый стол — отдельная локальная учётная запись Windows в собственной интерактивной сессии со своими окнами, вводом, звуком и видеопотоком, который отдаётся в немодифицированный клиент Moonlight. Пользователь за физическим монитором (консольная сессия) продолжает работать как обычно.

Исходные исследования и их независимое ревью лежат в [`docs/research/`](research/). Утверждения, которые ещё не подтверждены на железе, вынесены в раздел 8 как лабораторные тесты MVP.

## 1. Ключевые решения

| Вопрос | Решение | Почему |
|---|---|---|
| Изолированный стол | Отдельная RDP-сессия Windows на пользователя, созданная loopback-подключением к самому себе (127.0.0.2). Одновременные сессии на клиентской Windows даёт TermWrap (MIT, патч termsrv в памяти). Он ставится по умолчанию, как у Duo, а риск лицензии раскрывается в установщике (решение владельца проекта от 2026-10-28). Режима Windows Server RDSH нет. | Только у отдельной сессии свои DWM, очередь ввода, аудио-эндпоинт и winlogon. `CreateDesktop` внутри одной сессии изоляции не даёт. Так же устроены Duo и Chrome Remote Desktop. |
| Создание сессии | `splitplay-seat.exe` на libfreerdp (Apache-2.0), по одному процессу на стол, в сессии 0 | Пароль не попадает в командную строку, редиректы (буфер, диски, USB, микрофон) выключены, звук в null-приёмник. Python (aardwolf, как у Duo) не нужен. |
| Захват и виртуальный дисплей | Целевой вариант: собственный **remote-session IDD** (UMDF2, IddCx 1.4, для HDR 1.10) и тонкий нативный провайдер-обёртка над `rdpcorets` на RDP-Tcp. IDD копирует кадр на GPU в кольцо разделяемых текстур, откуда его забирает воркер. **В MVP**: DXGI Desktop Duplication внутри обычной RdpIdd-сессии (около 60 Гц). | Только захват на стороне IDD даёт высокую частоту без перекодирования RDP. Внедряться в RdpIdd через перехват смещений, как Duo, не будем: такое ломается каждым обновлением. |
| Сервер Moonlight | Форк upstream **Sunshine** («SplitPlay Worker», C++), один процесс на стол | Собственная реализация протокола (пейринг, RTSP, ENet+AES-GCM, RTP+FEC, Opus, около 30 типов ввода, RFI) заняла бы 9–15 чел.-мес. Форк обходится в 2–4. Совместимость с клиентами Moonlight уже проверена Sunshine. |
| Кодирование | Прямой NVENC SDK (P1, ultra-low-latency, бесконечный GOP, RFI, intra-refresh). По умолчанию HEVC, AV1 на Ada/Blackwell. AMF и QSV через FFmpeg как второй эшелон. | У NVENC P1 1080p один движок даёт 930–1130 fps для HEVC (официальные цифры NVIDIA). Это единственный путь с запасом на 500 Гц. |
| Ввод | Клавиатура и мышь: `SendInput` из воркера с SYSTEM-токеном в сессии стола (как у Chrome Remote Desktop). Геймпады: собственный драйвер на базе libvirtualgamepad (MIT, UMDF2 + VHF, профили DS4/DualSense/Xbox Series). Служба ставит устройству `DEVPKEY_Device_SessionId` до его старта, HidHide работает как страховка. | Физические клавиатура и мышь принадлежат консольной сессии, а `SendInput` действует только в сессии вызывающего процесса. ViGEmBus снят с поддержки, X360 (XUSB) не изолируется по сессиям. libvirtualhid из Sunshine нельзя распространять (лицензия LizardByte SAL). |
| Звук | WASAPI loopback эндпоинта «Remote Audio» своей сессии (стерео), Opus 48 кГц | Эндпоинт у каждой сессии свой, поэтому изоляция получается без глобальных виртуальных устройств. Объёмный звук позже, через свой посессионный аудиодрайвер. Интерфейс аудиоконвейера сразу многоканальный. |
| Служба, менеджер, UI | `SplitPlay.Service` на C#/.NET 10 (LocalSystem). Веб-интерфейс (Vue) на `:38299` через Kestrel. Трей-приложение с GUI на WebView2 открывает тот же веб-интерфейс. CLI `splitplay.exe`. | Удобный доступ к WTS, LSA, SCM, ACL и брандмауэру. Один UI на GUI и веб. Всё, что загружается в TermService, пишем только на нативном C++ без CLR. |
| Установщик | Inno Setup 6, один подписанный `SplitPlay-Setup-x.y.z.exe`, сборка в GitHub Actions | Нативно даёт один exe, бесплатен, установку драйверов, служб и правил брандмауэра легко описать скриптом. WiX v6+ требует платы Open Source Maintenance Fee, а MSI нам не нужен. |
| Лицензия | Воркер (форк Sunshine) под **GPL-3.0**, его исходники публикуем. Служба, UI, драйверы и провайдер остаются под **MIT** (как сейчас в репозитории). | Взаимодействие только через процессы, CLI, файлы, HTTP/JSON и простые сообщения в pipe, то есть «mere aggregation» по GPL FAQ. Код Sunshine в службу не линкуется. |

|---|---|---|---|
| **SplitPlay.Service** («служба») | C# .NET 10 | Сессия 0, LocalSystem | Конфигурация, учётки и секреты (LSA), конечный автомат каждого стола, запуск и перезапуск дочерних процессов (каждый в своём Job Object), порты и брандмауэр, Web API и SPA на 38299, агрегация метрик, оркестрация пейринга, самопроверка TermWrap и провайдера при старте |
| **splitplay-seat** | C++ (libfreerdp) | Сессия 0 | Держит loopback RDP-подключение одного стола: NLA, канал rdpsnd с null-выходом, все редиректы выключены. Переподключается по команде службы |
| **splitplay-rdsprov.dll** | C++ (нативный) | Внутри TermService | Оборачивает `rdpcorets` и всё делегирует ему. Для loopback-подключений SplitPlay отвечает на `IWRdsWddmIddProps` аппаратным ID нашего IDD. Вводится на Этапе 4 |
| **SplitPlay IDD** | C++ UMDF2 IddCx | Отдельный WUDFHost на каждую сессию | Remote-session драйвер: режимы из Moonlight (до 500 Гц), выбор рендер-GPU (`IddCxAdapterSetRenderAdapter`), копирование кадра в кольцо из 2–3 разделяемых текстур (NT handle и keyed mutex). Если кольцо занято, кадр отбрасывается, а не блокирует DWM |
| **splitplay-worker** («агент стола») | C++ (форк Sunshine, MinGW) | Сессия стола, SYSTEM-токен с `TokenSessionId` = N | Протокол Moonlight, захват (кольцо IDD, в MVP DDA), конвертация в NV12/P010, кодирование, аудио, ввод, запуск приложений под токеном пользователя, локальный REST (`/api/pin`, `/api/clients/*`) только на loopback |
| **SplitPlay Pad** | C++ UMDF2 + VHF | Драйвер | Виртуальные DS4, DualSense и Xbox Series. Устройство уничтожается при закрытии хэндла, поэтому падение воркера не оставляет «призраков» |
| **Tray / GUI, CLI** («менеджер») | C# + WebView2; C# | Сессия пользователя | GUI показывает тот же веб-интерфейс. Токен доступа выдаётся через pipe с ACL (только администраторы). CLI нужен для скриптов: `splitplay desktop start <имя>` |

## 3. Потоки данных

**Видео:** игра в сессии N → DWM этой сессии (частота композиции = `DWMFRAMEINTERVAL`) → swap chain нашего IDD → GPU-копия в разделяемую текстуру (≈0,1 мс) → воркер: шейдер в NV12/P010 → NVENC → RTP с FEC Рида — Соломона и опциональным AES-GCM → UDP (база+9) → Moonlight. Всё происходит на одном GPU, без копирования через CPU.

**Ввод:** Moonlight → управляющий канал ENet с AES-GCM (база+10) → воркер. Клавиатура и мышь идут через `SendInput` (относительная мышь, скан-коды), а перед каждой инъекцией воркер переключается на текущий input desktop (`OpenInputDesktop`/`SetThreadDesktop`), чтобы работали UAC и экран блокировки. Ctrl+Alt+Del отправляет служба через `SendSAS`. Геймпады воркер создаёт через Pad-драйвер, и служба привязывает их к сессии N. Ввод физических устройств хоста в сессию N не попадает: Windows отдаёт его только консольной сессии.

**Звук:** приложения → «Remote Audio» сессии N (seat-клиент объявляет rdpsnd, `audiomode=0`, но сам ничего не воспроизводит) → WASAPI loopback в воркере → Opus → AES-CBC и FEC → UDP (база+11).

**Порты:** у стола k базовый порт `P = 47989 + 100·k` (настраивается). Занимаются P−5 (HTTPS), P (HTTP), P+9, P+10, P+11 и P+21 (RTSP). В Moonlight стол добавляется как `IP:P`. Каждый воркер имеет свои `uniqueid` и сертификат, поэтому клиент видит столы как разные ПК. Имена в mDNS имеют вид `HOST-<стол>`. RDP 3389 закрыт для всего, кроме loopback.

## 4. Жизненный цикл стола и взаимодействие компонентов

```mermaid
stateDiagram-v2
  [*] --> Defined: создан в конфиге
  Defined --> Provisioning: start
  Provisioning --> Connecting: учётка, права RDU, пароль в LSA
  Connecting --> SessionReady: seat открыл loopback RDP, получен SessionId
  SessionReady --> DisplayReady: IDD поднят, режим выставлен
  DisplayReady --> Ready: воркер запущен, порты слушаются
  Ready --> Streaming: клиент Moonlight подключился
  Streaming --> Ready: клиент отключился
  Connecting --> Recovering: ошибка или таймаут
  SessionReady --> Recovering
  DisplayReady --> Recovering
  Ready --> Recovering: воркер упал или health-check не прошёл
  Streaming --> Recovering
  Recovering --> Connecting: backoff 1, 2, 4 … 60 с
  Recovering --> Faulted: больше 5 сбоев за 10 мин
  Ready --> Stopping: stop
  Streaming --> Stopping: stop
  Stopping --> Stopped: воркер остановлен, сессия завершена
  Faulted --> Stopping
  Stopped --> Provisioning: start
```

Порядок взаимодействия «служба — агент — менеджер»:

1. Менеджер (веб, GUI или CLI) вызывает `POST /api/desktops/{id}/start`. Служба проверяет конфиг и бюджет GPU (раздел 5).
2. Служба запускает `splitplay-seat` и ждёт событие `WTS_SESSION_LOGON` для нужного пользователя. SessionId каждый раз определяется заново: после перезагрузки он меняется, поэтому в конфиге его не храним.
3. Служба дублирует свой токен, ставит `TokenSessionId` = N и запускает воркер через `CreateProcessAsUser` в отдельном Job Object (job не может охватывать несколько сессий). Воркер получает свой каталог конфигурации и pipe `\\.\pipe\splitplay\desk-<id>`.
4. Воркер шлёт `ready`, затем раз в секунду heartbeat с метриками (fps, битрейт, задержка кодирования, потери, загрузка GPU и NVENC). Если 3 heartbeat подряд пропущены, служба убивает воркер и перезапускает его. Остальные столы при этом не затрагиваются.
5. «Pair New Client»: менеджер показывает форму PIN, служба передаёт PIN в `POST /api/pin` нужного воркера по loopback с одноразовыми учётными данными этого воркера. Список клиентов и отзыв доступа делаются так же, через `/api/clients/*`.
6. Автозапуск: служба стартует автоматически (delayed-auto) и поднимает столы с флагом `autostart`. Трей запускается при входе пользователя.

**Границы изоляции сбоев.** Сбой игры, воркера, DWM сессии или WUDFHost нашего IDD затрагивает только свой стол. Общими для всех столов остаются TermService (его перезапуск роняет все сессии), сброс GPU (TDR, затрагивает в том числе консоль) и драйверы ядра. Поэтому служба восстанавливает столы идемпотентно, а провайдер в TermService держим минимальным.

## 5. Как достигаются 500 Гц и где реальный потолок

Цепочка рассчитана так, чтобы ни одно звено не ограничивало частоту ниже 500 Гц:

1. **Композиция.** В remote-сессиях DWM ограничен значением `DWMFRAMEINTERVAL` (целые мс, по умолчанию 33 мс, то есть 30 fps). Ставим 4 мс (250 Гц) по умолчанию и 2 мс в профиле «500 Гц». Параметр глобальный для всех remote-сессий, поэтому служба выставляет его по самому быстрому активному столу.
2. **Дисплей.** IDD объявляет режимы до 500 Гц (`vSyncFreq = 500/1`). Режим выбирается автоматически под `mode=WxHxFPS` клиента.
3. **Захват.** Кадры приходят по событию из IDD, опроса нет. Воркер выдаёт кадры точно с частотой клиента: таймер `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION`, повтор последнего кадра, если изображение не менялось. У WGC-пути Sunshine есть ограничение 250 Гц (`MinUpdateInterval(4ms)`), но этот путь мы не используем.
4. **Кодирование.** NVENC P1, HEVC Main (уровень 5.2 допускает около 515 fps при 1080p). H.264 при 500 fps требует уровня 6.0, поэтому в профиле «500 Гц» по умолчанию HEVC или AV1. CBR с VBV в один кадр, без B-кадров и lookahead, RFI вместо IDR, intra-refresh против всплесков. Один поток не превышает пропускную способность одного движка NVENC.
5. **Сеть.** Протокол Moonlight без изменений: 60–150 Мбит/с, около 11–16 тыс. пакетов/с, проводной Ethernet. На хосте нужен 2,5 GbE, если столов несколько.
6. **Клиент.** moonlight-qt разрешает свою частоту от 10 до 9999 fps и битрейт до 500 Мбит/с (экспериментальный разблок). Для 500 Гц нужны декодер с HEVC L5.2 и экран 360–500 Гц. Android по умолчанию ограничен 120 Гц.

**Контроль допуска.** У каждого GPU есть бюджет примерно 900–1100 «1080p-эквивалентных кадров в секунду» на движок NVENC. На GeForce действует лимит 12 одновременных сессий кодирования на всю систему, и OBS с ShadowPlay в него тоже входят. Стол, который не помещается в бюджет, стартует с пониженным fps и предупреждением.

**Честный потолок (до лабораторного подтверждения):**

| Железо | Гарантируем | Best effort |
|---|---|---|
| NVIDIA Ada / Blackwell | 1080p 240–250 Гц на 2–3 стола | 1080p500 на 1–2 стола, 1440p500 на грани |
| NVIDIA Turing / Ampere | 1080p 240 Гц | 1080p500 на 1 стол |
| Intel Arc | 1080p 240 Гц | 720p500 |
| AMD | 1080p 144 Гц | 240–360 Гц (публичных замеров нет) |

Практический предел при нескольких столах задаёт не энкодер, а рендеринг игр и композиция DWM на общем GPU. Если `DWMFRAMEINTERVAL=2` на практике не даёт 500 Гц, мы задокументируем 333 или 250 Гц как реальный потолок. Это допускается критериями готовности.

**Бюджет задержки (оценка).** При 1080p500: захват ≈1 мс, конвертация 0,2 мс, кодирование ≈1 мс, отправка и сеть ≈1 мс, декодирование 1–3 мс, вывод ≈1 мс, итого 5–8 мс. При 1080p60 видео укладывается в 20–35 мс (цель ≤ 50 мс). Ввод: сеть и ENet меньше 2 мс, `SendInput` меньше 1 мс, так что цель ≤ 30 мс определяется частотой кадров игры.

**Дополнительные видеофункции.** Суперсэмплинг: IDD выставляет режим выше потока, воркер уменьшает его шейдером перед NVENC. Принудительный SDR и яркость белого: в HDR-режиме IDD отдаёт SDR white level, воркер выполняет tone-map. HDR: IddCx 1.10 (FP16), Windows 11 23H2+, P010/HEVC Main10. Масштаб рабочего стола: per-monitor DPI через `IddCxAdapterDisplayConfigUpdate`.

## 6. Конфигурация, безопасность, сборка

- **Конфиг:** `C:\ProgramData\SplitPlay\config.json`. Версионированная JSON-схема, валидация при загрузке, атомарная запись через временный файл и `MoveFileEx`. У каждого стола свой каталог `desktops\<id>\` с конфигом воркера (генерируется из `config.json`), сертификатами, `state.json` (пейринг, uniqueid) и логами. Каталог закрыт ACL: доступ только у SYSTEM и администраторов.
- **Секреты:** пароли пользователей столов (генерируются случайно) хранятся в LSA private data, учётные данные воркеров и хэш пароля веб-интерфейса (Argon2id) — в DPAPI-machine.
- **Импорт и экспорт:** zip с `config.json` и сертификатами пейринга. Секреты включаются только по запросу и шифруются паролем экспорта.
- **Веб-интерфейс:** по умолчанию слушает только localhost. Доступ из LAN включается флагом: тогда HTTPS с самоподписанным сертификатом, пароль администратора, ограничение частоты запросов и CSRF-токены. Ошибки показываются там же: логи служебных процессов, метрики через WebSocket.
- **Логи:** структурированные JSON-строки с ротацией в `ProgramData\SplitPlay\logs`. Отдельно — ETW-провайдер для драйверов.
- **Репозиторий:** `service/` (.NET), `worker/` (сабмодуль-форк Sunshine с очередью патчей), `seat/`, `drivers/idd`, `drivers/pad`, `rdsprov/`, `web/` (Vue), `installer/` (Inno), `docs/`.
- **CI (GitHub Actions, windows-2022):** воркер собирается в MSYS2 UCRT64, служба через `dotnet publish` (self-contained), драйверы через MSBuild с WDK из NuGet, затем Inno Setup и подпись. Пользовательский код подписывается Azure Artifact Signing, драйверы — через EV и attestation в Partner Center. Сквозные тесты с GPU и мультисессиями требуют self-hosted раннера на Windows 11 с NVIDIA.
- **Установщик** ставит службу, файлы, драйверы (`pnputil /add-driver /install`), правила брандмауэра по диапазонам портов, политики RDP (WDDM, тайм-ауты отключения, `DWMFRAMEINTERVAL`) и WebView2. TermWrap ставится всегда. На странице лицензии установщик прямо говорит, что патч termsrv нарушает лицензию Windows для клиентских редакций. Деинсталлятор возвращает настройки RDP и TermService, удаляет драйверы и правила брандмауэра, а учётные записи пользователей не удаляет без подтверждения.

## 7. Риски и ограничения платформы

| # | Риск | Влияние | Как снижаем |
|---|---|---|---|
| 1 | **Лицензия Windows.** Одновременные сессии на клиентской Windows нарушают §2(c)(iv) и (v) EULA. Патч нужен и «чистому» пути через IDD (NonRDPPatch). | Юридический и репутационный риск, детекты антивирусов | Принятый риск (решение владельца проекта): TermWrap по умолчанию, риск раскрыт в установщике и README, юридическая консультация до публичного релиза |
| 2 | Обновления Windows меняют termsrv, rdpcorets и IddCx | Столы перестают подниматься после Patch Tuesday | Самопроверка при старте, откат в режим «только консоль», CI-кольцо на Release Preview, TermWrap ищет точки патча во время выполнения |
| 3 | Remote-session IDD — свежий R&D (первый успех в OpenStreamMS был 2026-10-27, известен дедлок при снятии с остановкой, требующей перезагрузки) | Сдвиг сроков Этапа 4 | MVP на DDA, IDD в отдельной ветке за флагом, стресс-тесты жизненного цикла |

Минимальная ОС: Windows 11 Pro или Enterprise 24H2 (26100) и выше. Для HDR нужна 23H2+ с IddCx 1.10. Поддержка Home не гарантируется. У учётных записей столов обязателен пароль: этого требует NLA, а учётные записи Microsoft не поддерживаются.

## 8. Этапы, сроки и проверки

Оценка дана для команды из 3–4 инженеров, один из которых знает драйверы Windows и RDS. Код пишу я, поэтому календарные сроки этапов 2–3 могут быть короче, но сквозные тесты требуют реального ПК с Windows 11 и GPU NVIDIA: в облачном CI нет GPU и мультисессий.
