# Research 7 (round 2, "max-out"): video pipeline latency and frame rate
Code read: Sunshine d7e5fe0, moonlight-common-c 5d3c0ec, moonlight-qt ac29686, OpenStreamMS 33794bf, nv-codec-headers f205307 (NVENC API 13.1). ms figures are estimates unless sourced; (unverified) marked.

## Code findings that matter
1. Sunshine capture loop (display_base.cpp::capture) sleeps to the next slot (group_start + k/fps) then grabs newest frame with timeout 0 → a frame arriving just after a slot waits up to one stream interval; pacing group resets on miss. Unlocked rates: average extra ≈ ½ interval (≈8.3 ms @60, 1 ms @500).
2. Encode fully serial: one registered input texture, one bitstream buffer (nvenc_base.cpp::encode_frame): convert → nvEncEncodePicture → wait → LockBitstream → thread queue → videoBroadcast.
3. Send pacing 80% of 1 Gbps per session (stream.cpp ratecontrol_packets_in_1ms) → wire time ≈ frame size / 100 MB/s (1080p60 @100 Mbps ≈ 208 KB ≈ 2.1 ms).
4. Wire format allows block-by-block send: each packet carries its FEC block's data-shard count (RtpVideoQueue.c:709) and 2-bit block index + last-block index; Sunshine MAX_FEC_BLOCKS=4; Sunshine 8-byte frame header lastPayloadLen used only by AV1 (VideoDepacketizer.c ~910) → for HEVC/H.264 the first packet can leave before encode finishes; not for AV1.
5. moonlight-qt D3D11VA: FLIP_DISCARD, 5 buffers, Present(0, ALLOW_TEARING) with V-Sync off; advertises HEVC/AV1 RFI; never requests intra-refresh; after IDR request drops non-IDR frames (waitingForIdrFrame).
6. IddCx: IDDCX_METADATA.pSurface always A8R8G8B8; driver may use it until next ReleaseAndAcquire; PresentDisplayQPCTime gives intended display time; empty dirty rect = unchanged; no vsync/flip/composition-timing control. OpenStreamMS: one shared texture + keyed mutex AcquireSync(0), drop if busy.
7. NVENC 13.1: enableSubFrameWrite returns slices/tiles as done (app polls); reportSliceOffsets needs sync mode; SFE incompatible with subframe mode and video-memory output; RGB input converted internally via CUDA, "minimal" impact (programming guide).
8. Sunshine nvprefs sets "prefer maximum performance" only for a profile bound to sunshine.exe → renamed worker loses it.

## Ranked ideas
1. **Encode on arrival (replace slot sampler)** — IDD backend waits on frame event/fence, converts+encodes immediately; token bucket caps average at client fps; min gap ≈0.75/fps; repeat last frame only for a minimum rate; skip "unchanged" dirty rects. Gain: up to ½ interval avg (≈8 ms @60, 4 @120, 1 @500) when game/DWM not locked to stream; frees NVENC on idle desks. Cost 1–2 pw. Risk: uneven arrival — fine with V-Sync off/VRR client, judder with Moonlight frame pacing on. Set minimum_fps_target 10–20.
2. **Client setup guide** — Moonlight fullscreen (independent flip), V-Sync off, frame pacing off, D3D11VA, HEVC, stream fps ≥ display refresh, VRR on. Gain: removes client DWM + vsync queue, 1–2 refreshes (16–33 ms @60 Hz client, 4–8 @240). Likely largest single item. Cost 0. Verify with PresentMon "Hardware: Independent Flip".
3. **Control game render queue via NVAPI DRS** — frame cap at/just below GPU-sustainable, Ultra Low Latency for DX11, in-game Reflex. Gain: 1–2 game frames (10–30 ms) when GPU-bound; NVIDIA claims up to 33% (2019 article). Also stops A's game starving B's DWM/encoder. Risk: per exe, machine-wide.
4. **GPU clocks/priority** — bind worker exe (not sunshine.exe) to "prefer maximum performance"; realtime/high GPU priority for worker + IDD host (Sunshine downgrades to high with HAGS); test raising each desk's dwm.exe priority via D3DKMTSetProcessSchedulingPriorityClass as SYSTEM (unverified). Gain ≈0.5–2 ms at idle clocks (unverified), lower tails.
5. **Shorter IDD→encoder path** — IDD does one pass from pSurface into a 3-texture ring NVENC encodes directly (BGRA→NV12 shader in IDD or ARGB fed to NVENC with internal CUDA conversion); copy on D3D12 copy queue (copy engine, not behind game 3D); shared fences instead of keyed mutex + CPU event; worker registers ring once, drops own convert. Gain 0.1–0.5 ms/frame (more under load), saves ≈4 GB/s bandwidth/desk @1080p500. Cost 2–3 pw. Risk: cross-process shared texture with NVENC; CUDA conversion under load (unverified). HDR still needs shader → P010.
6. **One thread per desk pipeline** (wait → encode → packetize/FEC → send) with MMCSS + CPU sets; removes two queue hand-offs. Gain 0.05–0.5 ms avg, removes multi-ms tail spikes (unverified). Adds to patch queue.
7. **Network tuning** — per-desk configurable pacing rate (>800 Mbps on 2.5 GbE+, adjusted for active desks), 10% FEC wired, VBV one frame, prefer higher fps (smaller frames). Gain 0.3–1 ms wire time @1080p60 100 Mbps, more on IDR.
8. **Slice streaming (HEVC/H.264)** — enableSubFrameWrite=1, reportSliceOffsets=1, sync mode, 4 slices; each slice = one FEC block; all packets declare 4 blocks; polling thread sends each block when its slice completes. Gain ≈¾·min(encode, wire): ≈0.7–1.5 ms @1080p60 high bitrate, ≈0.2 ms @500 Hz, several ms on IDR. Cost 2–4 pw. Risk: not with AV1/SFE; slices cost ~1–3% bitrate (unverified); polling CPU; unmodified Moonlight acceptance unverified on the wire.
9. **Late cursor** — IDD HW cursor (IDDCX_ADAPTER_FLAGS_REMOTE_ALL_CURSOR_POSITION), worker draws cursor at latest position in convert pass → pointer motion no longer forces recompose; 1–5 ms cursor latency gain (desktop/RTS). Conflicts with raw-ARGB-to-NVENC unless drawn in copy pass.
10. **SFE for one fast desk** — NV_ENC_SPLIT_TWO_FORCED_MODE (Sunshine nvenc_split_encode): ≈1.8× → ≈0.4–0.5 ms less encode @1080p (unverified), makes 1440p500 feasible; ≈2% compression loss, both engines used, no slice streaming.
11. **DWMFRAMEINTERVAL 2–4 regardless of client fps** — with #1 the composition wait becomes 1–2 ms; DWM believed to compose only on change (unverified); V-Sync games may lock to it → cap games (#3).
12. **Exotic: encoder inside IDD host (WUDFHost)** — NVENC per desk encodes pSurface ARGB directly, holds buffer until consumed, bitstream to worker via shared memory. Gain 0.2–0.5 ms. Cost high; needs own MIT NVENC code for GPL cleanliness; encoder hang kills the desk's display adapter; holding buffers may stall DWM. Only after measurement.
13. **Exotic: Present-hook game capture** (OBS graphics-hook style) — skips composition (1–2 ms @2–4 interval, up to 8 ms vs 60 Hz compose), escapes DWMFRAMEINTERVAL, enables host-side Reflex-like alignment. Very high risk (anti-cheat, cursor/overlays, per-API hooks, crashes in game). Per-game opt-in.

**Measurement first:** PresentMon ETW consumer per desk; IDD PresentDisplayQPCTime + acquire QPC + worker timestamps; set Sunshine frame_timestamp to IDD present time (Moonlight "host processing latency" overlay then covers compose→send); glass-to-glass with OSLTT/LDAT.

**Possible 1080p60 host-side after #1, #4, #5, #7 (est):** ≈1 ms compose wait + 0.2 convert + 1 encode + ≈0.5 send + 0.2 network + 1–2 client decode ≈ 4–5 ms + scan-out, vs plausible 10–20 ms today.

## Rejected
Host independent flip/DirectFlip/MPO (IDD gets only DWM's composed ARGB; no planes/flip API; no exclusive fullscreen); reading before DWM finishes (no API; compose ≈0.1–0.3 ms); IDD driving DWM timing by holding buffers (no vsync API, stalls session); intra-refresh replacing IDR (Moonlight waits for real IDR → freeze; keep RFI; continuous intra-refresh only for lossy links); AV1 for latency (not faster, no early slices, slower decode on many clients); lookahead/B-frames/2-pass/multi-frame in flight; client slice decoding / bigger packets (needs fork, D3D11VA decodes whole pictures).
